# Требования к прототипу автоматизации Яндекс Метрики и Яндекс Директа

Версия: `2.0-prototype`.
Дата: 29 июля 2026 года.
Статус: исходные требования с внесёнными правками review addendum v1.3.
При конфликте addendum исправляет исходное требование.
Enterprise-рекомендации, не необходимые прототипу, в обязательный scope не входят.

## Назначение документа

Документ сохраняет структуру и идентификаторы `06-validated-requirements.md` и вносит в него продуктовые и технические исправления из `review-addendum-yandex-ads-prototype-v1.3.md`.
Прототип состоит из модуля мониторинга и модуля безопасного управления одной кампанией.
Документ описывает проверяемое поведение компактного прототипа, а не enterprise-платформы.

## Подтверждённые условия проекта

### Цель

Прототип должен проверить один управляемый цикл:

`связанные данные Директа и Метрики → метрики → LLM-анализ → предложение → policy check → подтверждение человека → изменение → readback → наблюдение результата`.

Модуль мониторинга читает данные одной кампании и одного счётчика, связывает их, рассчитывает показатели, обнаруживает проблемы и формирует объяснимую рекомендацию.
Модуль управления подготавливает структуру кампании и выполняет ограниченное действие только после явного подтверждения оператора.
LLM не получает OAuth-токены, произвольные endpoint или прямой write-доступ.
Прототип доказывает корректность измерения и безопасность исполнения, но не гарантирует рост KPI и не доказывает причинный эффект.

### Объём

В прототип входят:

- Один локальный оператор.
- Один тестовый аккаунт Яндекса для тестовых интеграций.
- Один разрешённый рекламный аккаунт и одна разрешённая пилотная кампания для real read и controlled pilot.
- Один поддерживаемый тип кампании.
- Одна группа, одна ключевая фраза или один поддерживаемый таргетинг и одно объявление.
- Один активный и один заранее подготовленный резервный вариант объявления.
- Одна ручная стратегия `HIGHEST_POSITION`, если её поддерживает выбранный тип кампании.
- Один разрешённый счётчик Метрики.
- Одна основная цель и одна отдельная кандидатная тестовая цель.
- Одна тестовая страница для проверки события цели.
- Исходные локальные fixtures.
- Чтение реальной статистики при наличии доступа.
- Создание полной структуры кампании в подтверждённом тестовом контуре.
- Разовый и плановый read-only анализ.
- Режимы `OBSERVE`, `RECOMMEND` и `APPROVAL_REQUIRED`.
- Одно вручную подтверждённое обратимое действие на allowlisted пилотной кампании.
- Readback и отчёт о наблюдаемом результате.
- CLI и локальные артефакты.

Фактические типы созданных объектов сохраняются из ответа API.
До реализации фиксируется матрица `тип объекта → версия API → среда → методы`.
Она устраняет конфликт между исходным `v5` и управлением ЕПК через `v501`.

В прототип не входят:

- Несколько клиентов или кампаний.
- Произвольные типы кампаний.
- Автономные production-write без подтверждения каждого proposal.
- Долговременные Mandate и отдельные криптографические человеческие роли.
- Изменение production-сайта и существующих production-целей.
- Автоматическое удаление production-объектов.
- Генерация изображений или видео.
- Веб-интерфейс.
- CRM, коллтрекинг и офлайн-конверсии.
- Платный хостинг и облачное развёртывание.
- Микросервисы, высокая доступность и горизонтальное масштабирование.
- Enterprise audit anchor, write-once storage и сложные production-saga.
- Статистическое доказательство превосходства рекламного варианта.

### Обязательные решения до реализации

Следующие решения должны быть зафиксированы до начала реализации и не могут быть выбраны разработчиком молча:

| Решение | Обязательный результат |
| --- | --- |
| Основная бизнес-конверсия и микроконверсии | Идентификаторы, классификация и бизнес-смысл |
| Модель атрибуции | Одно нормативное значение для snapshot |
| Тип кампании и стратегия | Один поддерживаемый тип и применимая стратегия |
| API-матрица | Object type, `v5` или `v501`, environment, host, path, service, method и verification status |
| Пилотный scope | Allowlisted account, campaign, counter, goal и единственный writer |
| Controlled-pilot действие | Один точный обратимый action и его readback |
| Риск controlled pilot | Денежный cap, loss threshold и stop condition |
| Свежесть | Числовые значения freshness, watermark и cutoff поздних конверсий |
| Мониторинг | Числовые значения интервала polling, anomaly thresholds и observation window |
| Результат impact evaluation | Имя поля и машинное кодирование четырёх вариантов: сохранить, откатить, скорректировать или передать человеку |
| Данные LLM | Разрешённые поля и срок хранения артефактов |

Пороговые значения из локальных fixtures применяются только к этим fixtures и sandbox-проверкам.
Они не разрешают production-write и не считаются рекомендациями для реальной рекламы.
Реализация операций Direct не начинается до выбора поддерживаемого типа кампании и заполнения нормативной API-матрицы.
Любой production-write блокируется, пока остальные решения этой таблицы не утверждены.

### Ответственность

Разработчик отвечает за:

- Сбор, уточнение и документирование функциональных и нефункциональных требований.
- Своевременную подачу заявок и выполнение действий, необходимых для получения доступа к API Яндекса.
- Подготовку всех тестовых аккаунтов, приложений, счётчиков, целей, клиентов и кампаний.
- Оформление и настройку всех необходимых тестовых доступов, включая OAuth-доступы.
- Разработку прототипа.
- Автоматическое и ручное тестирование.
- Установку, запуск и эксплуатацию.
- Техническую поддержку, диагностику и исправление ошибок.
- Проведение демонстрации и подготовку итогового отчёта.

Заказчик отвечает только за:

- Валидацию и подтверждение требований до начала разработки.
- Оценку и приёмку уже разработанного и протестированного прототипа.

### Срок

Семидневный срок исходной версии не является жёстким критерием приёмки, потому что addendum признаёт его нереалистичным после расширения сценария.
Новый срок должен быть согласован после фиксации обязательных решений и доступов до начала реализации.
Если обязательный доступ своевременно запрошен, но не предоставлен Яндексом, соответствующий результат получает `INCONCLUSIVE`.
После фиксации заказчиком итогового статуса приёмки production-write отключается.
Переход к MVP оформляется отдельно.

## Часть I. Функциональные требования

### 1. Данные и интеграция

#### 1.1 Какие данные должен получать прототип?

ID требования: `FR-001`

Ответ:

Прототип должен формировать `IntegratedPerformanceSnapshot` со следующими полями:

- `snapshot_id` и версия схемы.
- Разрешённые organization, connection, account, campaign, counter и goal.
- `period_start`, `period_end`, часовой пояс `UTC` и модель атрибуции.
- Grain `campaign × goal × day`.
- Источник, время получения и watermark каждого блока.
- `impressions`, `clicks`, `cost_micros`, `visits` и `goal_visits`.
- `currency` со значением `RUB`.
- CTR, CPC, конверсия, CPA, pacing и отклонение от baseline.
- Текущие бюджет, стратегия, ставка или ограничение стратегии и вариант объявления.
- Состояние кампании, группы и объявления.
- Последние изменения с автором и временем, бизнес-цель и целевой KPI.
- Пробелы качества данных, `comparability_status` и доверительный статус вывода.

Директ предоставляет статистику и состояние разрешённой кампании.
Метрика предоставляет `ym:s:visits` и `ym:s:goal<goal_id>visits`.
В локальных fixtures исходное поле `conversions` означает число целевых визитов и нормализуется в `goal_visits`.
Связь campaign, counter и goal задаётся доверенной конфигурацией и подтверждённым правилом сопоставления идентификаторов кампании, цели, UTM, `yclid`, атрибуции и периода.
Данные разных периодов, часовых поясов или моделей атрибуции нельзя считать сопоставимыми.
`comparability_status` принимает `COMPARABLE`, `PARTIAL` или `INCOMPATIBLE`.
Доверительный статус учитывает минимальную выборку и свежесть данных.
`PARTIAL` разрешает только нефинансовые выводы и запрещает финансовую рекомендацию или proposal.
`snapshot_id` считается по всем нормативным полям, включая organization, connection, campaign, период, модель атрибуции, метрики, состояние, управляемые значения, версию конфигурации объекта и policy version.
Закрытый период, правило включения НДС, допустимая разница watermarks и cutoff поздних конверсий фиксируются до реализации.
Поздняя конверсия создаёт новую версию snapshot и не изменяет старую.
Локальный fixture разрешён для проверки логики, но не выдаётся за реальную связанную аналитику.

#### 1.2 Какие основные операции Яндекс Директа должен выполнять прототип?

ID требования: `FR-002`

Ответ:

Исходная матрица сохраняется как тест connector и executor:

- `Campaigns`: `add`, `get`, `update`, `suspend`, `resume`, `archive`, `unarchive`, `delete`.
- `AdGroups`: `add`, `get`, `update`, `delete`.
- `Ads`: `add`, `get`, `update`, `suspend`, `resume`, `archive`, `unarchive`, `moderate`, `delete`.
- `Keywords`: `add`, `get`, `update`, `suspend`, `resume`, `delete`.
- `KeywordBids`: `get`, `set`.

Для каждого метода сохраняется отдельный результат и readback либо проверка удаления.
Для `add` подтверждаются новый идентификатор, фактический тип и последующее чтение.
Для `update` и `set` подтверждается точное новое значение.
Для `suspend`, `resume`, `archive` и `unarchive` подтверждается новое состояние.
Для `moderate` подтверждается принятие запроса без требования промышленного результата модерации.
Для `delete` подтверждается отсутствие объекта.
`Campaigns.update` проверяет `WeeklySpendLimit`.
`AdGroups.update` проверяет изменение названия тестовой группы.
`Keywords.update` проверяет `UserParam1`.
`KeywordBids.set` проверяет `SearchBid`.
`Ads.update` проверяет установку подготовленных заголовка и текста.
Архивирование и удаление разрешены только для объектов текущего тестового запуска.
Интеграционный тест соблюдает допустимую последовательность состояний Яндекса.
До теста сохраняется исходное состояние.
После теста исходное состояние восстанавливается либо удаляются только созданные текущим запуском объекты.
Эта матрица не является списком прямых LLM-tools.

Пользовательский модуль предоставляет высокоуровневые команды создания draft и кампании, получения показателей, подготовки proposal, применения подтверждённого плана, изменения бюджета и ставки, смены варианта, pause, resume и оценки результата.
API-матрица фиксирует фактические host, version, object type, service, method, environment и verification status.
Заполненная API-матрица является нормативным приложением к настоящему документу.
Неизвестная комбинация блокируется до запроса.
В production разрешается только метод одного заранее утверждённого controlled-pilot действия.

#### 1.3 Какие метрики должен рассчитывать прототип?

ID требования: `FR-003`

Ответ:

Прототип рассчитывает:

- CTR как `clicks / impressions * 100`.
- CPC как `cost_micros / clicks / 1 000 000`.
- Конверсию как `goal_visits / visits * 100`.
- CPA как `cost_micros / goal_visits / 1 000 000`.
- Использование бюджета как `cost_micros / current_weekly_budget_micros * 100`.
- Pacing относительно ожидаемого расхода на текущий момент периода.
- Отклонение от доступного baseline.

При нулевом знаменателе возвращается `NOT_APPLICABLE`.
Пороги сравниваются по неокруглённым значениям.
В JSON сохраняются исходные значения и неокруглённые результаты.
Для отображения применяется `ROUND_HALF_UP` до двух знаков.

Сохраняются исходные policy-пороги:

- Целевой CPA `1 000 ₽`.
- Расход без конверсий `2 000 ₽`.
- Минимум `50` кликов и `3` конверсии.
- Низкий CTR менее `1%` при не менее `5 000` показов.
- Использование бюджета не менее `90%`.
- Низкий трафик от `50` до `99` кликов.
- Изменение бюджета или ставки за шаг `10%`.

Read-only polling выполняется с заданным до реализации числовым интервалом.
Финансовый proposal запрещён при нарушении заданных до реализации числовых границ freshness или допустимой разницы watermarks.
Числовое observation window после write фиксируется до реализации.
Анализ запускается при расходе без конверсий, аномальном pacing, заметном отклонении CTR, CPC или conversion rate, прекращении срабатывания цели, несовместимости источников, внешнем изменении кампании или нарушении freshness.
Порог учитывает абсолютную сумму, время внутри бюджетного периода, день недели, сезонность, размер выборки, задержку конверсий, недавние изменения кампании и известные сбои сайта или трекинга.
До реализации числовые значения фиксируются отдельно для опережения pacing, роста расхода без роста конверсий после учёта задержки, отклонения CPC, CTR и conversion rate от baseline, прекращения срабатывания цели, расхождения источников и нарушения freshness.
Одинаковая причина для одного snapshot не должна создавать несколько активных proposals.

#### 1.4 Как прототип должен проверять входные данные?

ID требования: `FR-004`

Ответ:

До анализа проверяются:

- Наличие и тип обязательных полей.
- Целочисленность, неотрицательность и отсутствие `NaN` или бесконечности.
- `clicks <= impressions` и `goal_visits <= visits`.
- Валюта `RUB`.
- Разрешённые account, campaign, counter и goal.
- Совпадение периода, часового пояса и атрибуции.
- Provenance, watermarks и свежесть.
- Соответствие `snapshot_id`.
- Положительный недельный бюджет.
- Отсутствие неизвестного внешнего изменения кампании.

Для локального fixture дополнительно требуются `source = LOCAL_FIXTURE`, период ровно семь календарных дней, закрытое окончание не старше сорока восьми часов и положительный целочисленный недельный бюджет.
Техническое чтение тестового счётчика сохраняется как отдельный `AnalyticsReadResult` с `source = METRICA_TEST_COUNTER`, разрешёнными counter и goal, закрытым периодом и неотрицательными целочисленными visits и goal visits.
Прошедший все применимые проверки объект получает статус `READY`.
Нарушение обязательной проверки даёт статус `REJECTED`.
Критическая ошибка даёт `INCOMPATIBLE`.
Недостаточная выборка даёт `INSUFFICIENT_DATA`.
Устаревшие данные запрещают финансовый write-proposal.
Статусы `INCOMPATIBLE`, `INSUFFICIENT_DATA` и `REJECTED` также запрещают финансовый write-proposal.
Ошибка trusted scope блокирует изменяющий контур.
При `REJECTED` LLM не вызывается, а результат содержит `NEEDS_HUMAN`, `REQUEST_HUMAN_HELP` и применимый `reason_code` без write.

### 2. Решение агента

#### 2.1 Какое решение должен формировать агент?

ID требования: `FR-005`

Ответ:

LLM получает нормализованную проекцию проверенного snapshot, бизнес-цель, историю разрешённых изменений и policy limits.
LLM не получает OAuth-токены, endpoint, credential profile, полный API-ответ или право выбрать target ID.

В зависимости от задачи LLM возвращает один из трёх отдельных типизированных объектов: `OptimizationProposalV1`, `CampaignDraftV1` или `GoalCandidate`.
Ни один из этих объектов не содержит произвольный HTTP payload.
Для оптимизации LLM возвращает `OptimizationProposalV1`:

- `proposal_id`, версия предложения, `run_id`, `snapshot_id`, время создания и expiry.
- `status` со значением `EFFECTIVE`, `INEFFECTIVE`, `INSUFFICIENT_DATA` или `NEEDS_HUMAN`.
- Наблюдаемые факты.
- Не более трёх ранжированных гипотез.
- Упорядоченный набор атомарных действий с зависимостями, лимитами и отдельными условиями отмены.
- `evidence_fields` как непустой массив уникальных ссылок только на реально присутствующие поля snapshot.
- Ожидаемое направление эффекта и минимальное окно наблюдения.
- Риски, предусловия, условие отмены и запрос недостающих данных.
- Точный ожидаемый diff и expected fingerprint.
- `explanation_ru` на русском языке длиной от `1` до `500` символов.

Допустимые действия оптимизации: `KEEP`, `INCREASE_WEEKLY_BUDGET`, `DECREASE_WEEKLY_BUDGET`, `INCREASE_SEARCH_BID`, `DECREASE_SEARCH_BID`, `SET_AD_VARIANT`, `SUSPEND_CAMPAIGN`, `RESUME_CAMPAIGN` и `REQUEST_HUMAN_HELP`.
Каждое атомарное действие содержит поля `action` и `parameters`.
`EFFECTIVE` допускает `KEEP`, `INCREASE_WEEKLY_BUDGET`, `INCREASE_SEARCH_BID` или `RESUME_CAMPAIGN`.
`INEFFECTIVE` допускает `KEEP`, `DECREASE_WEEKLY_BUDGET`, `DECREASE_SEARCH_BID`, `SET_AD_VARIANT` или `SUSPEND_CAMPAIGN`.
`INSUFFICIENT_DATA` допускает только `KEEP`.
`NEEDS_HUMAN` допускает только `REQUEST_HUMAN_HELP`.
Для `SET_AD_VARIANT` параметры содержат только обязательный `variant_id` со значением `A` или `B`.
Для `REQUEST_HUMAN_HELP` параметры содержат только обязательный `reason_code`.
Для остальных исходных действий параметры пусты, а техническое целевое значение вычисляет детерминированный слой.
JSON Schema запрещает неизвестные поля через `additionalProperties: false` и не допускает произвольный HTTP payload.
В текущем прототипе executable `OptimizationProposalV1` содержит ровно одно высокоуровневое действие.
Невалидный ответ отклоняется без write.
LLM отделяет факты от гипотез и запрашивает данные при неоднозначности.
LLM объясняет ситуацию на языке бизнеса и отличает вероятную проблему рекламы от проблемы трекинга или сайта.
Ошибки используют reason codes `INVALID_INPUT`, `AMBIGUOUS_DATA`, `UNSUPPORTED_STATE`, `UNSUPPORTED_ACTION`, `AGENT_ERROR`, `API_ERROR`, `OUT_OF_BOUNDS` или `UNKNOWN_RESULT`.

#### 2.2 Как прототип должен выбирать и проверять действие агента?

ID требования: `FR-006`

Ответ:

В `OBSERVE` прототип только собирает данные и формирует объяснение, не создаёт write-proposal и не вызывает executor.
В `RECOMMEND` прототип создаёт proposal, но не применяет approval и не вызывает write.
В `APPROVAL_REQUIRED` прототип выполняет write только после одноразового подтверждения точной версии proposal.
Автономные production-write не входят в прототип.
LLM не обязана повторять единственное действие, заранее рассчитанное таблицей.
Policy независимо проверяет schema, evidence, scope, freshness, fingerprint и безопасность.

Сохраняются исходные safety-условия:

- Увеличение бюджета разрешено для `ON`, достаточной выборки, CPA не выше `1 000 ₽` и использования бюджета не ниже `90%`.
- Уменьшение бюджета разрешено для `ON`, достаточной выборки, CPA выше `1 000 ₽` и использования бюджета не ниже `90%`.
- Увеличение ставки разрешено для `ON`, ручной стратегии, достаточной выборки, CPA не выше `1 000 ₽`, использования бюджета ниже `90%` и `50–99` кликов.
- Уменьшение ставки разрешено для `ON`, ручной стратегии, достаточной выборки, CPA выше `1 000 ₽` и использования бюджета ниже `90%`.
- Смена варианта разрешена для `ON`, достаточной выборки, CTR ниже `1%`, не менее `5 000` показов и другого варианта.
- Pause разрешён для `ON`, нулевых конверсий и расхода не меньше `2 000 ₽`.
- Resume разрешён для `SUSPENDED`, не менее `3` конверсий и CPA не выше `1 000 ₽`.

`KEEP` и `REQUEST_HUMAN_HELP` не отправляют write-запрос.
Эти числовые условия проверяют fixtures и sandbox, но не разрешают controlled-pilot write.
Для controlled pilot применяются отдельно утверждённые числовые limits и monetary cap из раздела обязательных решений.
Недопустимое действие блокируется.
За один run допускается не более одного утверждённого высокоуровневого действия.
Тестовое `create_campaign` считается одним высокоуровневым действием и может выполнить несколько внутренних sandbox-write под одним `execution_key`.
Изменение snapshot, target, diff или fingerprint требует нового proposal и подтверждения.
Идемпотентный ключ решения включает organization, connection, campaign, период, модель атрибуции, метрики, состояние кампании, текущие бюджет, ставку и вариант объявления, версию конфигурации объекта и policy version.
Execution key дополнительно включает утверждённый proposal, целевое действие, целевое значение и expected object version.

### 3. Действия и результаты

#### 3.1 Какие действия агента должен выполнять прототип?

ID требования: `FR-007`

Ответ:

LLM предлагает высокоуровневое действие, а скрипт проверяет и исполняет его.

Высокоуровневый контракт содержит `create_campaign_draft`, `validate_campaign_draft`, `create_campaign`, `create_ad_variant`, `validate_ad_copy`, `get_campaign_performance`, `propose_optimization_plan`, `apply_approved_plan`, `set_weekly_budget`, `set_search_bid`, `set_strategy_constraint`, `set_ad_variant`, `pause_campaign`, `resume_campaign` и `get_change_impact`.
Внутренние технические команды ограничены следующими путями:

- `set_weekly_budget(target_value)` вызывает `Campaigns.update`.
- `set_search_bid(target_value)` вызывает `KeywordBids.set`.
- `set_ad_variant(variant_id)` вызывает `Ads.update` с подготовленными заголовком и текстом.
- `set_campaign_state(target_state)` вызывает `Campaigns.suspend` или `Campaigns.resume`.

`CampaignDraftV1` содержит бизнес-цель и основную конверсию, поддерживаемый тип кампании и стратегию, географию и расписание, бюджет и предельные ограничения, группы, ключевые и минус-фразы либо аудитории, тексты и заголовки, ссылки и UTM, allowlisted посадочную страницу и ссылки на подготовленные медиа-материалы.
Детерминированный слой проверяет schema, ограничения полей, домен посадочной страницы, запрещённые формулировки, дубликаты и полноту.
После проверки `CampaignDraftV1` orchestrator сохраняет immutable proposal высокоуровневого `create_campaign` с точным diff.
В тестовом контуре `create_campaign` после approval выполняет одну бизнес-транзакцию: dry-run, создание кампании, группы, объявления и ключевой фразы, сохранение ID и фактических типов, отправку на модерацию, отслеживание статуса, запуск и полный readback.
Тот же тестовый lifecycle проверяет настройку, изменение бюджета и допустимых параметров, pause и resume.
Повтор с тем же `execution_key` не создаёт вторую структуру.
Создание новой production-кампании в текущем прототипе не требуется; controlled pilot выполняется на одной заранее разрешённой кампании.

`GoalCandidate` содержит название, событие, место на сайте, тип, бизнес-смысл, приоритет и признаки дубликата.
Детерминированный слой проверяет schema, разрешённый тестовый counter и отсутствие конфликтов.
`GoalCandidate` проходит собственный lifecycle и не является действием из enum `OptimizationProposalV1`.
Подтверждение оператора на создание разрешает только новую кандидатную цель в тестовом counter и не подтверждает её бизнес-смысл.
После создания цель получает статус `CANDIDATE`.
На тестовой странице устанавливается `reachGoal`, а Playwright проверяет ровно одну отправку события.
Отдельный polling с заданными до реализации интервалом и общим тайм-аутом `T_METRIKA` проверяет появление целевого визита через API Метрики.
Результат `INCONCLUSIVE` допустим только при доказанной внешней задержке или недоступности.
Доказательство включает идентификатор и тип цели, селектор или событие, сценарий теста, факт отправки, факт появления целевого визита, отсутствие двойного срабатывания, классификацию основной конверсии или микроконверсии, дату, автора и версию настройки.
После проверки человек отдельно подтверждает либо отклоняет бизнес-семантику.
Только статус `APPROVED` разрешает использовать цель в оптимизации.
Отклонённая кандидатная цель исключается из решений и очищается без изменения существующих или исторических целей.

Production-сайт и существующие production-цели не изменяются.
После pilot write формируется новый snapshot и `impact_report.json` со статусом `OBSERVED_POST_CHANGE`.
Impact report можно передать LLM для следующей рекомендации, но новое действие требует нового proposal и подтверждения.

#### 3.2 Как прототип должен защищать изменяющее действие?

ID требования: `FR-008`

Ответ:

Перед write проверяются:

- Режим `APPROVAL_REQUIRED`.
- Флаг `automation_enabled`.
- Подтверждение точной версии proposal.
- Успешный `dry_run` и точный diff.
- Allowlisted host, version, service и method.
- Target из доверенной конфигурации.
- `COMPARABLE` и свежий snapshot.
- Достаточная выборка.
- Текущее состояние и expected fingerprint.
- Числовые limits и pilot monetary cap.
- Отсутствие другого write.
- Неиспользованный execution key.

CLI показывает target, значения до и после, diff, риск и expiry.
Для прототипа достаточно интерактивного подтверждения без криптографических ролей.
Локальное приложение сохраняет `Approval`, привязанный к canonical hash из organization, connection, target, точного diff, snapshot и его timestamps, policy version, expected fingerprint и expiry.
LLM не может создавать или изменять `Approval`.
Executor принимает `proposal_id`, самостоятельно загружает proposal и атомарно помечает одноразовый `Approval` использованным.
До использования подтверждение можно отозвать.
Изменение proposal, snapshot, target, diff, policy version, fingerprint или expiry требует нового подтверждения.
Каждая изменяющая команда имеет типизированные вход и выход, organization, connection, допустимый объект, `dry_run`, точный diff, предусловия, expected fingerprint, числовые limits, `proposal_id`, `execution_key`, readback и обратную команду либо явный признак необратимости.
Целевое значение рассчитывается как `current × 1.10` или `current × 0.90` с `ROUND_HALF_UP`.
Выход за границы даёт `OUT_OF_BOUNDS` без прижимания к лимиту.

До первого HTTP write высокоуровневого действия `ExecutionLedger` атомарно резервирует unique `execution_key`, после чего запись получает `IN_FLIGHT`.
После write проверяются HTTP-результат, object errors, warnings и readback.
Целевое состояние даёт `APPLIED`.
Уже установленное состояние даёт `NO_CHANGE`.
Исходное состояние после timeout даёт `FAILED` без повтора.
Неопределимое состояние даёт `UNKNOWN_RESULT` и блокирует следующий write.
Повтор execution key и параллельный write не создают второе изменение.
`APPLIED` или `NO_CHANGE` закрывает execution key, а повтор возвращает `ALREADY_PROCESSED` без нового write.
`BLOCKED` или `FAILED` можно повторно проверить после устранения причины.
`UNKNOWN_RESULT` запрещает новый write до ручного согласования фактического состояния.
Direct API не даёт универсальную compare-and-set гарантию, поэтому перед write сравнивается canonical fingerprint, команды сериализуются, а на время пилота назначается единственный writer.

#### 3.3 Какие результаты должен создавать прототип?

ID требования: `FR-009`

Ответ:

Каждый run создаёт `runs/<run_id>/`.
Каждый run обязательно создаёт `result.json`, `report.md` и `events.jsonl`.
По фактически выполненным этапам дополнительно создаются `proposal.json`, `approval.json`, `change_diff.json` и `impact_report.json`.
Артефакты содержат версии schema и policy, `run_id`, `snapshot_id`, источник и период данных, provenance, исходные показатели, метрики, proposal, результаты проверок и код блокировки, техническую команду, значения до и после readback, конечное состояние объекта и итоговый статус.
JSON-артефакты сохраняют исходные и неокруглённые значения.
`report.md` содержит краткий отчёт на русском языке.
`result.json` также содержит provider и model ID, число токенов, стоимость и длительность этапов.
Поле `execution_status` принимает `NOT_STARTED`, `IN_FLIGHT`, `APPLIED`, `NO_CHANGE`, `BLOCKED`, `ALREADY_PROCESSED`, `UNKNOWN_RESULT` или `FAILED`.
Журнал показывает предложение LLM, решение policy и результат executor.
`impact_report.json` содержит baseline и post-change periods, watermarks, задержку конверсий, сезонность, известные вмешательства и confounders, изменения метрик, confidence, evidence и статус `OBSERVED_POST_CHANGE`.
Результат оценки содержит ровно одно следующее решение: сохранить изменение, откатить его, скорректировать или передать человеку.
Имя поля и точное машинное кодирование этих четырёх вариантов фиксируются до реализации; до этого schema `impact_report.json` не утверждена.
Без заранее утверждённого экспериментального дизайна результат не называется причинным эффектом.
Итоговый отчёт отдельно показывает каждую capability, её статус, тип и пути evidence, а также ограничения.
Скрытые рассуждения и секреты не сохраняются.
Enterprise audit anchor и hash-chain не требуются.

## Часть II. Нефункциональные требования

### 1. Производительность и среда

#### 1.1 Какую нагрузку и скорость должен поддерживать прототип?

ID требования: `NFR-001`

Ответ:

Прототип последовательно обрабатывает по одному активному account, campaign, counter и goal в каждом разрешённом контуре.
Тестовая структура и пилотная кампания не используются одновременно в одном run.
Основная и кандидатная цели имеют разные идентификаторы и состояния.
Fixture содержит не более `1 000` записей.
`decision_run` имеет тайм-аут `10` минут, а его локальная часть — `5` минут.
`integration_test_run` имеет тайм-аут `20` минут.
Write с readback имеет тайм-аут `2` минуты.
Read-only scheduler работает с числовым интервалом, зафиксированным до реализации.
Параллельное управление и масштабирование не проверяются.

#### 1.2 В какой среде должен работать прототип?

ID требования: `NFR-002`

Ответ:

Прототип должен работать на одной локальной машине разработчика с macOS.
Основные компоненты должны запускаться через Docker и управляться через командную строку.
Небольшой хостовый запускатель разрешён только для чтения OAuth-токена из macOS Keychain и безопасной передачи токена контейнеру на время запуска.
Облачная, Linux- и отдельная промышленная серверная среда не создаются и не проверяются.

### 2. Безопасность, устойчивость и стоимость

#### 2.1 Как должны защищаться данные и доступы?

ID требования: `NFR-003`

Ответ:

Прототип не использует прикладные персональные данные.
Тестовая страница содержит только синтетический контент.
Технические данные тестового визита обрабатываются Метрикой только в объёме проверки счётчика и цели.
OAuth-токены хранятся в macOS Keychain и не попадают в prompt, env, argv, Docker metadata, код, stdout, exceptions или артефакты.
Названия кампаний и целей, объявления, URL и UTM, поисковые запросы, API warnings и errors, бизнес-бриф и DOM считаются недоверенными данными.
LLM получает только очищенные allowlisted поля с ограничением длины.
Инструкции внутри недоверенного текста не могут изменить policy, scope, target, approval или набор tools.

Используются логические профили:

- `DIRECT_PROD_READ` для production Reports без management connector и write-egress.
- `DIRECT_SANDBOX_WRITE` только для `api-sandbox.direct.yandex.com`, allowlisted методов и тестовых объектов.
- `METRIKA_TEST_WRITE` с минимальными `metrika:read` и `metrika:write` для одного тестового counter.
- `TEST_SITE_PUBLISH` только для тестовой страницы без права публикации на production-сайт.
- `DIRECT_PILOT_WRITE`, отключённый по умолчанию и ограниченный одной allowlisted кампанией, одним действием и platform-side spend cap.

Профили используют раздельные credentials из Keychain.
Read-only процесс не получает write credential.
Pilot credential получает только executor непосредственно перед разрешённым запросом.

Сеть разрешена только к endpoint из нормативной API-матрицы, `api-metrika.yandex.net`, `mc.yandex.ru` и одному model provider.
Разрешён только `https` на порту `443`.
Redirects и production-delete запрещены.
Временный секрет удаляется после run.
Локальные временные файлы удаляются не позднее двадцати четырёх часов после демонстрации.
Все OAuth-токены прототипа удаляются из Keychain или отзываются после фиксации заказчиком итогового статуса приёмки.
Архив без секретов хранится не более тридцати дней.

#### 2.2 Как прототип должен вести себя при ошибках?

ID требования: `NFR-004`

Ответ:

Одинаковые входные данные и policy version дают одинаковые расчёты.
После первоначальной временной read-ошибки допускается не более двух повторных попыток.
Write нельзя повторять без readback.
SQLite хранит `ExecutionLedger` с unique execution key и переходами `RESERVED → IN_FLIGHT → APPLIED / NO_CHANGE / BLOCKED / UNKNOWN_RESULT / FAILED`.
После рестарта оператор видит незавершённую операцию.
`UNKNOWN_RESULT` блокирует следующий write до ручной проверки.
Ошибка LLM, schema, policy или read до write не изменяет объект.
Необработанная ошибка останавливает run.
Сложные автоматические production-saga и compensation не требуются.

#### 2.3 Как должна ограничиваться стоимость прототипа?

ID требования: `NFR-005`

Ответ:

Общая стоимость использования модели в течение прототипа не должна превышать `2 000 ₽`.
Стоимость должна рассчитываться по числу входных и выходных токенов, включая повторные вызовы.
Тариф модели и курс пересчёта в рубли должны фиксироваться до первого запуска и записываться в отчёт без секретов.
При достижении `80%` лимита разработчик должен получить локальное предупреждение.
После исчерпания лимита новые вызовы модели должны блокироваться.
Механизм предупреждения и блокировки должен проверяться на синтетическом значении локального счётчика стоимости.
Платный хостинг не используется.

## Условия приёмки

Сохраняются восемь fixtures исходной спецификации:

- `BUDGET_INCREASE_ON`: `ON`, бюджет `5 500 ₽`, `10 000` показов, `200` кликов, `150` визитов, `10` конверсий, расход `5 000 ₽`.
- `BUDGET_DECREASE_ON`: `ON`, бюджет `8 000 ₽`, `10 000` показов, `200` кликов, `150` визитов, `5` конверсий, расход `7 500 ₽`.
- `BID_INCREASE_ON`: `ON`, бюджет `10 000 ₽`, ставка `100 ₽`, `5 000` показов, `80` кликов, `70` визитов, `8` конверсий, расход `4 000 ₽`.
- `BID_DECREASE_ON`: `ON`, бюджет `20 000 ₽`, ставка `100 ₽`, `10 000` показов, `200` кликов, `150` визитов, `5` конверсий, расход `7 500 ₽`.
- `LOW_CTR_ON`: `ON`, бюджет `10 000 ₽`, вариант `A`, `10 000` показов, `50` кликов, `100` визитов, `3` конверсии, расход `3 000 ₽`.
- `NO_CONVERSION_ON`: `ON`, бюджет `10 000 ₽`, `10 000` показов, `100` кликов, `80` визитов, `0` конверсий, расход `2 000 ₽`.
- `EFFECTIVE_SUSPENDED`: `SUSPENDED`, остальные значения как у `BUDGET_INCREASE_ON`.
- `INSUFFICIENT_ON`: `ON`, бюджет `10 000 ₽`, `1 000` показов, `20` кликов, `15` визитов, `1` конверсия, расход `500 ₽`.

Fixtures проверяют расчёты и safety policy, но не требуют единственного ответа LLM.
Для детерминированной проверки policy и executor в каждый fixture подаётся заранее названный proposal.
Тест проверяет допустимость действия, расчёт технического значения и readback, но не сравнивает живой ответ LLM с одним заранее определённым действием.
Ожидаемые пути этой проверки:

- Для `BUDGET_INCREASE_ON` policy допускает `INCREASE_WEEKLY_BUDGET`, а executor подтверждает бюджет `6 050 ₽`.
- Для `BUDGET_DECREASE_ON` policy допускает `DECREASE_WEEKLY_BUDGET`, а executor подтверждает бюджет `7 200 ₽`.
- Для `BID_INCREASE_ON` policy допускает `INCREASE_SEARCH_BID`, а executor подтверждает ставку `110 ₽`.
- Для `BID_DECREASE_ON` policy допускает `DECREASE_SEARCH_BID`, а executor подтверждает ставку `90 ₽`.
- Для `LOW_CTR_ON` policy допускает `SET_AD_VARIANT` с `variant_id = B`, а executor подтверждает подготовленные заголовок и текст варианта `B`.
- Для `NO_CONVERSION_ON` расчёт даёт CPA `NOT_APPLICABLE`, policy допускает `SUSPEND_CAMPAIGN`, а executor подтверждает `SUSPENDED`.
- Для `EFFECTIVE_SUSPENDED` policy допускает `RESUME_CAMPAIGN`, а executor подтверждает `ON`.
- Для `INSUFFICIENT_ON` policy допускает `KEEP`, и executor не отправляет write.

Каждая способность получает отдельный статус:

- `PROVEN` — все обязательные тесты способности пройдены и приложены артефакты.
- `NOT_PROVEN` — реализация, конфигурация или доказательства не соответствуют требованию либо доказана несопоставимость данных.
- `INCONCLUSIVE` — корректно начатый тест временно не завершён только из-за подтверждённой внешней недоступности или задержки.
- `NOT_TESTED` — проверка не выполнялась.

Тип evidence указывается отдельно: `SANDBOX`, `TEST_COUNTER`, `REAL_READ_ONLY`, `SIMULATED` или `CONTROLLED_PILOT`.

| Способность | Обязательна в текущем прототипе | Ожидаемое evidence |
| --- | --- | --- |
| `CAMPAIGN_LIFECYCLE` | Да, в тестовом контуре | `SANDBOX` |
| `GOAL_LIFECYCLE` | Да, для тестовой цели | `TEST_COUNTER` |
| `SOURCE_INTEGRATION` | Да | `REAL_READ_ONLY + CONTROLLED_PILOT` |
| `INTEGRATED_ANALYTICS` | Да | `REAL_READ_ONLY + CONTROLLED_PILOT` |
| `LLM_ANALYSIS` | Да | `SIMULATED + REAL_READ_ONLY` |
| `APPROVAL_REQUIRED` | Да | `SANDBOX + CONTROLLED_PILOT` |
| `BOUNDED_AUTONOMY` | Нет | Вне scope текущего прототипа |
| `MONITORING_AND_ALERTING` | Да | `SIMULATED + CONTROLLED_PILOT` |
| `IMPACT_EVALUATION` | Да | `CONTROLLED_PILOT` |
| `OPERATIONAL_MODES` | Да, для `OBSERVE`, `RECOMMEND` и `APPROVAL_REQUIRED` | `SIMULATED + CONTROLLED_PILOT` |
| `TOOL_CONTRACT` | Да | `SIMULATED + SANDBOX` |
| `ORIGINAL_INTEGRATION_COVERAGE` | Да | `SANDBOX + TEST_COUNTER` |
| `SAFETY_CORE` | Да, в границах FR-008 и NFR-003–004 | `SANDBOX + SIMULATED + CONTROLLED_PILOT` |
| `CLOSED_LOOP_CONTROL` | Да, для одного подтверждённого действия | `CONTROLLED_PILOT` |

Любой обязательный `NOT_PROVEN` даёт общий `NOT_PROVEN`.
При его отсутствии любой обязательный `INCONCLUSIVE` даёт общий `INCONCLUSIVE`.
Общий `PROVEN` возможен только при `PROVEN` всех обязательных способностей.
Успешная sandbox-проверка не доказывает production-write, а раздельные read-only данные и sandbox-write не доказывают closed loop.
Создание новой production-кампании, production-site publish, production goal lifecycle и `BOUNDED_AUTONOMY` отложены за пределы текущего прототипа и не могут получить в нём `PROVEN`.
Положительный рост KPI не является критерием приёмки.

## Проверенные ограничения Яндекса

- Для Direct API требуются OAuth-токен и одобренный доступ приложения.
- Песочница изолирована от реальной рекламы и может отличаться по типам объектов.
- Для операций `v5` песочница использует `https://api-sandbox.direct.yandex.com/json/v5/<service>`.
- У песочницы Директа нет веб-интерфейса.
- Песочница Директа использует реальные OAuth-токены.
- Фактические host, version и methods фиксируются в нормативной API-матрице.
- Управление ЕПК проверяется с учётом `v501`.
- Денежные значения передаются целыми микрорублями.
- `SearchBid` применим только к поддерживающей его ручной стратегии.
- Для недельного бюджета используется `WeeklySpendLimit`.
- Фактический тип созданного объекта может отличаться от compatibility-request.
- Для чтения Метрики требуется `metrika:read`.
- Для создания тестовой цели требуется `metrika:write`.
- Отдельной песочницы Метрики нет; обычный API ограничивается разрешённым тестовым счётчиком.
- Целевые визиты доступны через `ym:s:goal<goal_id>visits`.
- Reporting API не доказывает отсутствие двойного `reachGoal`, поэтому это проверяет Playwright.
- Данные Метрики могут задерживаться, поэтому учитываются freshness и observation window.
