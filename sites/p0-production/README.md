# MOX-ADV P0 for GPT Sites

Private GPT Sites production candidate for the first MOX-ADV campaign workflow.

The Context step verifies the exact configured Yandex Direct advertiser through official `clients.get` and the exact Yandex Metrika counter and goal through official Management APIs before it permits progress. It then researches only a DNS-verified public first-party HTTPS target with manual redirect handling, a four-redirect cap, at most six pages and a 5 MB streamed-response budget. Private/local/link-local resolutions, credential-bearing URLs, cross-party redirects and oversized responses fail closed. Before the longer Model analysis starts, the step persists the sanitized API/site facts and exactly one evidence-grounded provisional business goal; the owner must explicitly confirm or correct it.

The Site keeps all OAuth credentials server-side and persists revisioned state in D1. Exact package dispatch creates one deterministic durable execution identity per selected Draft and runs those item executions independently under one account-level writer lease. Each item records validation, creation, exact suspension, child graph, semantic readback, moderation, provider IDs/issues, ownership and containment. Definite contained provider or system failures do not erase or stop later safe items; ambiguous outcomes hold the account boundary and leave the remaining items queued. Every mutation body and fingerprint is journaled before its network call, bounded recovery uses only the exact item fingerprint and known provider IDs, and no write is blind-retried. The semantic readback rules are documented in [`docs/direct-provider-normalization.md`](../../docs/direct-provider-normalization.md). The Model step also presents a permanently labelled `ADVISORY · NON-BLOCKING` LandingAdvisoryRun for the exact approved Campaign Strategy revision and normalized final landing URL. The versioned injected audit harness requires Lighthouse `12.8.2`, Chrome `136.0.7103.113`, desktop config `p0-lighthouse-desktop-1920x1080-v1` and axe-core `4.10.3`; it records exactly five sequential 1920×1080 Lighthouse attempts and component medians only when all five succeed, plus bounded raw axe category counts/details and explicit incomplete/manual review. Its fail-closed browser policy permits credential-free GET/HEAD only to exact public first-party allowlisted hosts after DNS/IP checks, binds every connected request address back to that public resolution to prevent DNS rebinding, denies restricted/auth/admin paths and cross-party subresources, and disables clicks, forms, uploads, downloads, cookies and client storage. Every injected adapter operation receives a 30-second AbortSignal and must settle after cancellation before the harness starts the next sequential operation. Persisted observations are bounded and redacted. Observed Metrika behavior is copied only from the exact counter/goal evidence already persisted by official APIs; missing, partial or zero-visit coverage remains insufficient. Findings are typed `OBSERVED_FACT`, `DETERMINISTIC_CHECK` or visibly non-authoritative `LLM_HYPOTHESIS`. The run is a separate top-level advisory artifact and is never an input to eligibility, publish readiness, score, rank, thresholds, calibration or the canonical publish fingerprint. Deployments without the pinned injected browser runtime persist and render explicit insufficient evidence instead of claiming an audit.

The Model step emits one deeply immutable, content-addressed `p0-analytics-evidence-v2` snapshot with separately hashed source manifests, normalized claims, typed Evidence Records, bounded/redacted raw locators and values, transforms, versions, timestamps, conflicts and explicit gaps. First-party public observations, owner confirmations, official Direct API evidence, official Metrika API evidence and allowlisted public competitor observations remain distinct. Confidence stays a quality/freshness/consistency/coverage/uncertainty vector; Metrika sampling/privacy/lag and Direct read limitations remain attached, and unavailable current Direct inventory is a material blocker rather than zero activity. Competitor budgets, CPC, conversions, account state and internal strategy remain unavailable by policy. The same snapshot now persists official Wordstat `/v1/topRequests`, `/v1/dynamics` and `/v1/regions` observations under one batch identity with explicit operator/region/device scope. Unique assigned rows are summed once and labelled `LOWER_BOUND_OBSERVED_TOP_ROWS`; missing rows, partial responses, quota and provider failures remain `PARTIAL`/`UNAVAILABLE`, never zero. Pre-launch cost selects the first qualified source in strict Live 4 → comparable existing KeywordBids → comparable own-history order without averaging and otherwise remains explicitly unavailable. The production adapter verifies normalized phrase identity through official `Keywords.get` before reading `KeywordBids.get`; unavailable Live 4 capability/history and `AuctionBids=null` stay named unavailable observations rather than zero CPC. The Strategy step persists one versioned questionnaire with exactly 11 typed fields in canonical order: business goal, advertised offer, target audience, qualified result, exclusions, geography, period, landing page, weekly budget, target result cost and core message. Every row has exactly one recommendation (explicitly `null` when unsupported), a short operator explanation, one allowed source category and one simple status. Unknown geography, period and business-owned economics remain prepared decisions with consequences; Direct minimums and pre-launch cost evidence are constraints, never invented budget or target-cost defaults. The exact `APPROVE_CAMPAIGN_STRATEGY` command freezes normalized answers into one immutable revision linked to its questionnaire/version, Context revision/material fingerprint and exact Analytics Evidence Snapshot ID. Campaign Strategy then compiles persisted Demand Clusters into deterministic delivery buckets across goal, economics, geography, landing, message and management; compatible long-tail is packed, while a material split requires evidence-backed standalone capacity. The authoritative `campaign-fanout-v1` compiler evaluates the finite product × audience × offer × keyword-cluster ledger exactly once, emits one comparator plus at most two one-factor improvements per bucket, and stores a visible/hidden terminal audit record for every Draft or excluded rule candidate. Competitive naming requires the accepted versioned sample rule; otherwise the comparator is exactly `STRATEGY_BASELINE_FALLBACK`. A publishable new Draft must pin one injected, persisted `ACTIVE` + `APPROVED` content-addressed curated playbook release and only its active approved rules; quarantined, contradicted, deactivated, superseded, malformed, unapproved and unknown-version inputs are excluded fail closed. No governed release or approval is invented or bundled in the production default: until a real approved release is supplied, the application emits only an explicit `STRATEGY_BASELINE_FALLBACK` comparator, audits `PLAYBOOK_NO_ACTIVE_APPROVED_RELEASE`, and blocks publication. The core capability profile is fixed to Direct v501 `UNIFIED_CAMPAIGN` / `UNIFIED_AD_GROUP`, Search `WB_MAXIMUM_CLICKS`, Network `SERVING_OFF`, explicit keywords and `TEXT_AD`. Conditional provider fields require persisted official API plus exact-account eligibility evidence; unsupported selected fields remain in the attempted projection, produce an explicit publication blocker and are never silently dropped. Draft identity pins Strategy/Draft revisions, capability profile ID/version and playbook release/rule lineage; the `sha256:` publish fingerprint canonicalizes only provider-declared unordered arrays and preserves ordered-array semantics. A material Strategy edit creates a new revision, regenerates the finite Recommendation Set and clears Draft/shortlist lineage, while whitespace and URL normalization preserve it. Material Context or Model edits invalidate downstream lineage; the UI discloses that cascade and both the contract and UI block confirmation while persisted recomputation is pending. Every mutation uses document-level `expected_revision` compare-and-swap, so stale tabs fail closed without field-level merging. After one exact Human Decision Gate it dispatches every selected Draft as an independent Direct v501 execution, explicitly calls `Campaigns.suspend`, requires `State=SUSPENDED` before that item writes any child object, submits the exact ad IDs for moderation, and repeats the suspended semantic readback. `Campaigns.resume` is not implemented.

`lib/p0-application.ts` is the authoritative `mox-adv.p0.application` query/command contract for the five-step path. `GET /api/p0` queries the contract and `POST /api/p0` sends a command with `expected_revision`; both Sites rendering and future Dashboard rendering consume the returned workflow truth table instead of deriving transitions from document fields. The contract owns the persisted document, including exactly one top-level `analytics_evidence_snapshot`, separate `landing_advisory_run`, Campaign Strategy, Recommendation Set, Campaign Draft and external outcome. Queries reuse that persisted snapshot and never recompute evidence from a newer provider read. A new evidence result requires a Model command and a new document revision. Baseline v1/v2/v3/v4 documents migrate their nested snapshot, Context lineage, optional advisory field and provisional one-Draft shortlist into the single v5 document without creating another evidence or Strategy store; content hashes plus persisted questionnaire order and metadata are verified before query reuse or downstream recommendations. Every successful migration or command advances one monotonic document revision through compare-and-swap; the exact package intent and each item dispatch/result checkpoint are CAS-persisted around the separately durable Direct execution journal. `analyze_site` persists provisional Context, and `confirm_context_goal` records the explicit owner decision before full analysis. A material Context edit records the affected Strategy, Recommendation Set, Campaign Draft, shortlist and confirmation lineage, clears those current projections and blocks confirmation until recomputation; normalization-only URL/whitespace changes do not create false invalidation. Evidence and scoring returned for a revision come from that persisted document rather than being recomputed during a query. Legacy Sites documents are upgraded only when their lineage can be reconstructed; malformed, unknown-schema or orphaned-outcome documents fail explicitly without being overwritten. Public research uses credential-free GET, manual redirects, DNS/IP checks, exact host allowlists for competitor pages and fail-closed redirect/SSRF/size limits. Snapshot, client and persisted artifacts redact credential and common PII patterns; no prompt, token, browser-cabinet data or model chain of thought belongs in the document. Production Wordstat collection uses the separate server-side `YANDEX_WORDSTAT_OAUTH_TOKEN` and registered `YANDEX_WORDSTAT_CLIENT_ID`, plus explicit comma-aligned `YANDEX_WORDSTAT_REGION_IDS`/`YANDEX_WORDSTAT_REGION_NAMES` and `YANDEX_WORDSTAT_DEVICE`; only `POST` calls to `api.wordstat.yandex.net` are allowed, and credentials never enter the batch or client state.

`lib/campaign-viability.ts` is the authoritative `viability-score/1.0.0` comparative contract. It evaluates hard eligibility and required `EVIDENCE_GAP` before dimensions, score, rank or hiding. Eligible Drafts receive `COMPARATIVE PRELAUNCH PRIORITY / NOT A PREDICTION` with exact weights: demand 18%, cost 12%, economics 20%, offer–audience fit 18%, Direct feasibility 12%, measurement readiness 10% and evidence quality 10%. An optional unknown makes its dimension a disclosed midpoint 50 and sensitivity recomputes unknown dimensions at 0/100 while known dimensions remain fixed. Exact score ties share rank only inside one immutable Recommendation Set revision and capability cohort. Score hiding requires sensitivity upper bound `<45`, evidence quality `>=60` and no unresolved required gap; structural reasons always win. Results persist contributions, bounded claim/evidence pointers, exact frequency/cost scopes, blockers, gaps, cohort/comparable-set IDs and all threshold gates. `LandingAdvisoryRun`, moderation/campaign outcomes, post-launch metrics, outcome learning and calibration are excluded from eligibility, dimensions, score, sensitivity, rank, hiding and score/publish fingerprints. Hard-blocked and evidence-gap Drafts remain reviewable but never enter shortlist or confirmation.

The Campaign Canvas renders the exact persisted Recommendation Set as keyboard-openable ranked cards with deterministic variant/evidence filters, rank/score ordering and explicit hidden-candidate audit reasons. Cards keep comparator/improvement, comparative score and semantic ties, sensitivity, evidence quality, scoped Wordstat frequency, one source-labelled pre-launch cost and publish blockers separate. Its modal right drawer consumes the persisted `direct-v501-draft-field-registry-v1`: every campaign, ad-group, explicit criterion, text-ad and current asset-capability field is classified as editable, fixed by Strategy, fixed by capability or conditionally not present. Only the canonical registry's six core fields are enabled, and the client derives its submission membership from that validated persisted registry; each field is validated server-side and round-trips into the exact Direct projection. Queries reject any same-schema registry content drift before UI rendering, while only a genuinely absent legacy registry is migrated; unknown fields fail closed. A canonical no-op reports that normalization created no Draft revision. A material edit creates the next immutable Draft revision and publish fingerprint, records safe previous/current values for every changed Direct pointer, and fully rescored/reranks the fixed membership with dimension, score, rank and concise policy deltas. The `mox-adv.p0.application` `1.9.0` contract also accepts an explicit recommendation recalculation against an injected governed playbook release. It compares exact active-release status, ID, version, digest and applied rule ID/version lineage independently from owner Draft revisions: unchanged lineage preserves the Recommendation Set, every Draft revision and all downstream decisions byte-for-byte, while a real change or rollback regenerates and invalidates downstream state. The bounded operator-facing `Рекомендация пересчитана` notice matches replacements by stable delivery/capability/variant semantics, reports unmatched additions/removals truthfully and never includes evaluator traces. The production default still injects no release and therefore stays fail closed.

`lib/campaign-decision-gate.ts` defines the authoritative ordered shortlist, immutable package review and Human Decision Gate persisted inside `p0-application-document-v6`. Card add/remove/positional-restore commands accept only a Draft choice and recompute exact Draft revision, publish fingerprint, Strategy revision, capability profile and Recommendation Set lineage server-side under document CAS. Hidden, hard-blocked and unresolved evidence-gap Drafts fail closed. The sticky Canvas footer renders the persisted ordered selections independently of display filters and opens a server-built, content-addressed package review containing exact Direct account/capability binding and Analytics Evidence Snapshot identity. Exact-token confirmation stores one content-addressed durable decision and timestamp for that reviewed authority; it performs no Direct call and explicitly states that later campaign dispatch, containment, moderation and evaluation are independent rather than one atomic transaction. Material Context, Model, Strategy, Draft, account/capability/evidence or playbook changes invalidate review and Gate with a bounded content-addressed reason, while normalization-only Draft saves and client-only filters preserve them. Same-schema shortlist, review and confirmation drift is rejected before query rendering. `lib/campaign-package-execution.ts` seals one non-atomic package journal with ordered per-item identities and independent ownership/containment outcomes; `dispatch_package` revalidates the exact Gate, current account and capability lineage before persisting any dispatch intent. The legacy single-Draft `confirm_creation` path remains unavailable from the truth table and UI.
